A **Local (stdio-only) MCP server** that gives a model-host client (such as
**opencode**) a safe, isolated environment to run arbitrary commands — a
**drop-in replacement for the host shell**.

Instead of letting the model use the host shell directly, the model drives
**mcp-sandbox**: for each session it provisions a **per-session, isolated Docker
container** with the required directories mounted in, executes arbitrary
commands **inside** that container, and destroys it **when the session ends**
(ephemeral). **Security is the top priority** — the sandbox is *more*
restrictive than the host, never less.

- **MVP scope:** the **Docker** backend. Apple Container and other backends are
  designed for but not yet implemented.
- **Deployment:** Local / **stdio-only** (`-mode stdio` default). No HTTP, no
  observability endpoint, no container image.

## Features

- Per-session, isolated, **ephemeral** Docker sandboxes.
- Execute arbitrary commands inside the sandbox (argument-array exec — **no
  shell**).
- The session `cwd` is mounted **1:1 at the same absolute path** (read-only by
  default; opt-in `rw` via `SANDBOX_CWD_MODE=rw`); files come from the image,
  the host, or the runtime — **mount + exec is the core mechanism**.
- **Hardened by default**: read-only rootfs, drop-all capabilities, no-new-
  privileges, seccomp, non-root user, bounded resources, network `none`, tmpfs
  working dir, auto-remove.
- **Immutable `Isolation` policy** the caller cannot weaken.
- Secret-safe output: a single redaction layer hides `secret:true` fields from
  all output and logs.
- Human-in-the-loop confirmation for destructive tools (client-side, see below).

## Security model

mcp-sandbox is built around a **deny-by-default** security model with **full
shell capability inside the sandbox**:

- The model-host gets **full permission to run shell commands** — but **inside
  an isolated, ephemeral Docker container**, never on the host.
- **What is not explicitly allowed is, by default, not available.** Access is
  granted explicitly: host directories only via `ALLOW_DIRS`, network is `none`
  by default, root inside is a scoped opt-in per `SudoPolicy`, package install
  is opt-in via provisioned images.
- The container is hardened (read-only rootfs, drop-all capabilities,
  no-new-privileges, seccomp, non-root user, resource limits) and **cannot be
  weakened by a caller** (immutable `Isolation`).
- Everything is **ephemeral**: the sandbox is **destroyed when the session
  ends**.

The practical effect: the model can run **any** command it needs, safely
confined — so the model-host no longer needs a host shell at all.

## Architecture & design

Full architecture, security model, tool surface and conformance are documented
in **[`SPEC.md`](SPEC.md)**. Agent working conventions are in
**[`AGENTS.md`](AGENTS.md)**.

Highlights:

- **DDD / Clean architecture** with top-level packages
  (`cmd/mcp-sandbox/`, `domain/`, `application/`, `infrastructure/`, `e2e/`) —
  no `internal/`.
- **Role-based backend interfaces** (`Backend`, `Lifecycle`, `Executable`,
  `Introspectable`) with capability dispatch via type-assertion
  and `ErrCapabilityNotSupported` — no stubs.
- **Constructor-register backend factory**; Docker registers in `init()` and is
  selected **lazily** on the first create (no outbound calls at startup).
- **Declarative tool framework**: each tool is a `ToolDef` with annotations,
  instructions, input/output schema and a redaction contract, wrapped by a
  shared handler pipeline (validate → access-log → dispatch → redact →
  structured output).
- **Session lifecycle**: `create → use → destroy`, immutable mounts, idle
  reaper, shutdown `DestroyAll`.

## Configuration

The server is configured via **environment variables** (Local / stdio server —
auth via environment, no HTTP headers).

| Env | Default | Description |
|-----|---------|-------------|
| `-mode` (CLI flag) | `stdio` | Launch mode. Local server is fixed to `stdio`. |
| `ALLOW_DIRS` | `[]` (none) | Permitted host directories for mounts (incl. the session `cwd`). Empty ⇒ deny all. |
| `ALLOW_SYMLINKS` | `false` | Allow following symlinks outside `ALLOW_DIRS` (unsafe; default off). |
| `DOCKER_HOST` | `unix:///var/run/docker.sock` | Docker daemon socket (unix). |
| `LOG_LEVEL` | *(unset ⇒ logging disabled)* | Enable + level. stdio logging is **on only when set**. |
| `LOG_FILENAME` | — | stdio log file path, `chmod 600`. |
| `LOG_FORMAT` | `text` | `text` or `json`. |
| `SANDBOX_IDLE_TIMEOUT` | `15m` | Idle reaper window. |
| `SANDBOX_CWD_MODE` | `ro` | Session `cwd` mount mode: `ro` (default) or `rw` (opt-in, global feature flag). |

Example:

```bash
export ALLOW_DIRS="/Users/me/projects/myapp"
export LOG_LEVEL=info
export LOG_FILENAME=/tmp/mcp-sandbox.log
./mcp-sandbox -mode stdio
```

### Transport, auth & TLS notes

- **Transport:** STDIO only. The server is spawned as a local child process by
  the model-host; it opens no network listener.
- **Auth:** environment variables only. **No OAuth2** — there is no upstream
  HTTP API to authorize against (see `SPEC.md` §3.3).
- **TLS:** **never implemented in-server** (S01). The server has no HTTP
  listener, so there is no in-server TLS surface. If the server is ever placed
  behind a network-facing gateway, TLS termination is the reverse proxy's job.

## OpenCode setup

Use mcp-sandbox as the execution environment for **opencode** instead of the
host shell.

### 1. Disable the host shell

In your opencode config (`opencode.jsonc`), deny the built-in `shell` tool:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "deny" }
  ]
}
```

This removes the host `bash`/shell tool; the model then uses the sandbox MCP
for command execution.

### 2. Register the mcp-sandbox MCP server

`mcp-sandbox` is a **Local / stdio** server, so register it as a **local** MCP
server:

```jsonc
{
  "mcp": {
    "servers": {
      "mcp-sandbox": {
        "type": "local",
        "command": ["mcp-sandbox", "-mode", "stdio"],
        "environment": {
          "ALLOW_DIRS": "{env:PWD}",
          "LOG_LEVEL": "info"
        }
      }
    }
  }
}
```

- `command` launches the `mcp-sandbox` binary (put it on `PATH` or use an
  absolute path).
- `ALLOW_DIRS` scopes which host directories the sandbox may reach; the session
  working directory is mounted **1:1** at the same absolute path (see
  `SPEC.md` §7.2).
- opencode passes its session id to the server (`_meta.ai.opencode/sessionID`),
  which the server uses to correlate and label sandboxes.
- Use `opencode mcp list` / `/mcps` to check the server is connected.

> **HITL note:** because mcp-sandbox is Local/stdio (no HTTP UI), destructive
> tools (`sandbox_destroy`, `sandbox_destroy_all`) require confirmation
> **client-side** by the operator — see `SPEC.md` §4.4.

## Tool surface

Grouped **read → write → delete** (S03):

- **Read** (`readOnlyHint: true`): `sandbox_list`, `sandbox_info`,
  `sandbox_stats`.
- **Write/update** (`readOnlyHint: false`, `destructiveHint: false`):
  `sandbox_create` (session `cwd` mounted 1:1 read-only by default, opt-in `rw`
  via `SANDBOX_CWD_MODE=rw`), `sandbox_exec` (write-classified; ANSI-sanitized;
  redacted argv).
- **Delete** (`destructiveHint: true`): `sandbox_destroy`, `sandbox_destroy_all`.

> **Files come from the image, the host, or the runtime — never via MCP
> file-write tools.** The session `cwd` is mounted 1:1, so the model-host writes
> files on the **host** and the container reads/executes them at the same path;
> runtime artifacts live in the writable tmpfs workspace. There are **no**
> `sandbox_read_file` / `sandbox_write_file` / `sandbox_copy_in` /
> `sandbox_copy_out` / `sandbox_install_package` tools — **mount + exec is the
> core mechanism** (`SPEC.md` §4.2, §7.2).

All tools are `openWorldHint: false` and carry per-tool annotations +
instructions (`SPEC.md` §4).

> **Human-in-the-loop (HITL) for destructive tools:** because this is a
> **Local / stdio-only** server with no HTTP UI (S12), destructive confirmation
> is implemented **client-side** — the model-host (opencode) obtains human
> confirmation before invoking `sandbox_destroy` / `sandbox_destroy_all`.

## Security

The sandbox **replaces the host shell**, so security is enforced by the server
and cannot be weakened by a caller (`SandboxSpec.Isolation` is immutable):

- Read-only rootfs; **drop-all capabilities** (minimal re-add); no-new-
  privileges; **seccomp** (default MVP profile; custom profile is mandatory
  roadmap); **non-root** user inside.
- Bounded `PidsLimit`, `Memory`/`MemorySwap`, `NanoCPUs`, `Ulimits`.
- **Network `bridge` by default** (Docker's default bridged network); `host` networking forbidden at policy level.
- tmpfs working dir (`rw,noexec,nosuid,nodev`); `AutoRemove=true`.
- Host filesystem access **only** via `ALLOW_DIRS`, read-only by default,
  symlink-safe (EvalSymlinks + open-then-verify + `O_NOFOLLOW`); the session
  `cwd` is the one sanctioned bind-mount (read-only default).
- Single **redaction layer** hides `secret:true` fields from all output and
  logs; secrets delivered as tmpfs `0600` files, never argv/image.
- Sessions use opaque `crypto/rand` ids with label-based Docker ownership.
- Supply chain: sandbox images **pinned by digest**, trusted registries,
  signed packages.

### Docker socket access (known limitation)

The Docker socket (`/var/run/docker.sock`) is effectively **root on the host**.
The server mitigates this by preferring a **rootless Docker** daemon or running
in an isolated environment with socket access confined to the server process.
Review and choose the socket access model appropriate to your host. See
`SPEC.md` §7.6.

## Development

### TDD workflow

All fixes/features are done TDD-style (T01): **@qa** writes tests first
(isolated context), **@developer** writes the implementation (isolated context).
Tests are never weakened to make the implementation pass.

- **Unit tests:** `make test` — `go test -race` + **coverage ≥ 95%** gate
  (fails below).
- **Mutation testing:** gremlins as a hard gate (80/80) — dedicated CI job.
- **e2e tests:** build-tagged (`//go:build e2e`), run via **`make e2e`** using
  the **go-docker-testsuite** harness (requires Docker).

### Quality gates

CI (GitHub Actions) binds to the **make interface** (R07) and enforces:
`make lint` (golangci-lint, gosec, govulncheck, go-arch-lint), `make test`
(race + coverage ≥ 95%), `make build` (goreleaser), `make e2e`, plus hard-gate
jobs for **gremlins** (mutation) and **gitleaks** (secret scan). Findings are
**fixed, not suppressed**. CI never mutates repository state.
